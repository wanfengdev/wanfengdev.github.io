## 不是"让 AI 替你写代码"

最常见的误解是：vibe coding = 不知道自己在干什么。事实恰恰相反。要让 AI 产出有用的代码，你需要：

- **清楚知道自己要什么** —— prompt 的精确程度与开发者的经验成正比。
- **评估产出** —— 分辨地道的代码和"能跑但随时会爆的定时炸弹"。
- **主导迭代** —— 知道何时纠偏、何时拒绝、何时接受。

Vibe coding 是以高速执行的高层设计。它不会消除对技术判断力的需求，而是**放大**了这种需求。

## 实践中的流程

如今一个典型的 vibe coding 循环是这样的：

1. **明确意图** —— 准确定义_做什么_和_为什么_。
2. **AI 快速起草** —— 拿到 70-80% 可用的功能代码。
3. **审查与引导** —— 纠正方向、明确不变量、补充上下文。
4. **迭代打磨** —— 经过几轮短迭代，直到结果足够扎实。
5. **测试与最终审查** —— 这一步绝不能跳过；缺乏监督的 AI 会引入技术债。

---

> 最有价值的不是纯粹的速度，而是 AI 把你从_认知滚动_中解放出来——就是那层横在你和真正问题之间的样板代码与语法。

## 哪些技能更值钱

Vibe coding 并没有让所有技术技能过时，而是重新分配了它们的价值：

**价值上升：**

- 架构与系统设计
- 判断哪些代码长期可维护的眼光
- 写出精确、带上下文的 prompt 的能力
- 代码审查与问题模式识别
- 对领域规则的了解（业务、安全、UX）

**相对重要性下降：**

- 背诵语法
- 手写样板代码
- 把每个库的 API 都记在脑子里

## 不只是技术变革，更是文化变革

一些开发者抵触 vibe coding，背后有一个合理的情绪原因：掌控感。亲手写下每一行代码，会让人觉得自己完全理解这个系统。但在大型项目里，这种感觉从来都有一部分是幻觉。

问题不是_我该不该用 AI？_而是_如何信任一个并非完全由自己写出来的系统？_答案一如既往：**测试、审查和判断力**。只不过现在要应用在更大的产出量上。

未来的开发者，不是产出代码最多的人，也不是最少用 AI 的人，而是用最好的工具、凭最好的判断力，构建出**真正能用的系统**的人。
